# Colly - AI agent instructions

This is a multi-tenant small business assistant (Next.js 16 App Router + Prisma + Supabase + a DeepSeek → Groq → OpenRouter AI chain). The most important repo-specific details follow.

## Commands

- `npm run dev` - start dev server (Next.js 16)
- `npm run build` - production build
- `npm run start` - run built app
- `npm run lint` - lint (eslint)
- `npm run typecheck` - `tsc --noEmit`
- `npm test` - unit tests (`tsx --test tests/*.test.ts`)
- `npm run seed` - full demo reset (`node prisma/seed.cjs`) — never against production
- `npm run academy:sync` - push `prisma/academy-content.cjs` to the DB without wiping tenants

Required before submitting changes: `npm run lint`, `npm run typecheck` and `npm test`
(CI runs exactly these three). Add a test when you change a pure helper in `lib/`, the
academy content, or a pricing/credit rule.

## Database & Prisma

- Schema: `prisma/schema.prisma` (Postgres). Every non-Business model is scoped by `businessId` with cascade from Business.
- Client singleton: `lib/prisma.ts` (global cached in dev to avoid connection pool exhaustion).
- Seed: `prisma/seed.cjs` (dotenv-loaded). Wipes all data (cascade-safe order). Creates business `test-biz-1` ("ABC Electronics"), demo owner `demo@colly.test` (password empty, `supabaseUserId` null), products, 3 conversations with messages (including one agent-sent message). Re-running is safe. Note: seed cannot create Supabase Auth user; signup with demo email links the unclaimed User row to auth. Academy content is read from `prisma/academy-content.cjs`: lessons are upserted by slug (agent progress survives), quiz questions and the final exam are replaced on each run.
- Use Prisma Accelerate mentioned in schema only if needed; not required locally.
- `Conversation.lastMessageAt` (newest message stamp) is denormalised and maintained by the `message_touch_conversation_activity` trigger from `prisma/migrations/20261026000000_qa_indexes`; app code never writes it, and the trigger leaves `updatedAt` alone (the Telegram takeover clock reads it). That migration also creates `pg_trgm` + `product_name_trgm_idx` (lib/tools.ts fuzzy search) and the composite Message/Conversation indexes the inbox, history and usage queries need.
- `Business.industry` (text, `@default("RETAIL")`, one of `RETAIL | HOTEL | SERVICES`) is the tenant's vertical. It is not cosmetic: `buildSystemPrompt()` appends the hotel-receptionist persona for `HOTEL` (see "Industry verticals" below). Migration `20261105000000_add_business_industry` is a single `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT 'RETAIL'`, so every pre-existing row is backfilled in place. It was applied by hand (`prisma db execute --file …` → `prisma migrate resolve --applied` → `prisma generate`), the same way `add_bookings` and `add_team_members` were, because `prisma migrate diff` also reports the raw-SQL trigram index and `Business` timestamp drift.

## Auth (Supabase)

- Server client: `lib/supabase/server.ts` uses `@supabase/ssr` with async `cookies()`; setAll swallows errors in Server Components (proxy refreshes session). Always create per request.
- Browser client: `lib/supabase/client.ts` uses `@supabase/ssr` createBrowserClient.
- Env: `lib/supabase/env.ts` reads `NEXT_PUBLIC_SUPABASE_URL` and either `NEXT_PUBLIC_SUPABASE_ANON_KEY` or `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (accepts both). Missing config throws explicit error.
- Auth helpers: `lib/auth.ts` - `getCurrentUser()` validates token via `supabase.auth.getUser()` and maps to DB User+Business (prefers `supabaseUserId`, falls back to email on unclaimed rows, links on first match). `getCurrentBusinessId()` returns tenant id or null. `requireAuth()` redirects to `/login` if no session; throws if session exists but no tenant linked (prevents redirect loop). `AuthUser` includes business fields.

## Chat / AI (DeepSeek → Groq → OpenRouter)

- Provider chain: `lib/ai.ts` (`askAI()`). There is no per-provider module any more; all three providers speak the OpenAI-compatible API through the `openai` SDK. `PROVIDERS` is ordered — `deepseek` (`deepseek-chat`, `DEEPSEEK_API_KEY` + optional `DEEPSEEK_BASE_URL`, default `https://api.deepseek.com`), `groq` (`openai/gpt-oss-120b`, `GROQ_API_KEY` + `GROQ_BASE_URL`), `openrouter` (`nvidia/nemotron-3-ultra-550b-a55b:free`, `OPENROUTER_API_KEY` + `OPENROUTER_BASE_URL`). `askAI()` walks the list in order, reports each provider's down/up state through `lib/alerts.ts`, and returns `provider: "fallback"` with a static reply when all three fail — callers must then refund the credits they reserved (see the dashboard assistant below). Overloads: no tools returns `string`, with tools returns the full `ChatCompletion`.
- Chat engine: `lib/chat-engine.ts` - `handleIncomingMessage({ businessId, customerPhone, message, skipCustomerMessage? })` returns an `EngineResult`. This is where all reply generation lives: resolves/creates the customer by phone, reuses latest conversation or creates new (status OPEN), saves the customer message (unless `skipCustomerMessage`), respects `conversation.pausedUntil` (human takeover), loads last HISTORY_LIMIT=20 messages (desc->reverse), builds the system prompt via `buildSystemPrompt()` (identity, optional business.description/hours, SYSTEM_PROMPT_RULES, tone last), loops tool calls up to MAX_TOOL_ROUNDS=2, computes AI usage, and saves the AI reply as sender "ai". Tool: `search_products` (defined in TOOLS) - returns up to 5 matches (name, price in Naira, stock, description); `runToolCall()` calls `searchProducts(businessId, query)` from `lib/tools.ts`; `readQuery()` defensively parses JSON args. Other tools: `search_faqs`, `find_similar_products`, `escalate_to_owner`, `generate_invoice_from_receipt` and `create_booking` — the last one books an appointment through `createBooking()` in `lib/tools.ts`, always for the **conversation's** customer (`runToolCall()` receives `conversation.customerId`; the model's own `customerId` argument is ignored, because a model cannot know a real id and a guessed one must never book for another customer). `create_booking` also takes an optional `checkOutDate`, which is the hotel mode's second date (see "Industry verticals"). Sender values stored: "customer", "ai", "agent".
- Chat route: `app/api/chat/route.ts` - now a thin adapter over `lib/chat-engine.ts`. Accepts `{ businessId?, customerId, message }`; authorizes via session or `X-Colly-Internal-Secret`, validates the customer belongs to the business, converts voice/image to text, then delegates to the engine. `audioUrl`/`imageUrl` are fetched server-side by the pipelines, so they are SSRF-checked first by `isPublicStorageUrl()` (in `lib/supabase/storage-path.ts`, shared with the avatar write/read path): https only, no credentials/odd port, host must equal `NEXT_PUBLIC_SUPABASE_URL`'s host and the path must start `/storage/v1/object/public/` — anything else is a 400. Maps engine `blocked` -> `{ reply: null, paused: true }` and `no_message` -> 400.
- Dashboard assistant: `isDashboardAssistant: true` on `POST /api/chat` is an owner-only path (no customer, no conversation) and is metered like any other AI reply — `chargeAiReply(user.businessId, business.channel)` reserves credits before `askAI()`, the route returns 402 with `LOW_CREDIT_MESSAGE` (`{ blocked: true, reason: "no_credits" }`) when the wallet cannot cover it, and refunds through `refundAiReply()` on a thrown error or `provider === "fallback"` (503, reason `ai_unavailable`).
- Escalation (a handoff must always land): `escalateConversation()` in `lib/chat-engine.ts` writes the onsite record FIRST — `Conversation.escalatedAt` + `status: "ESCALATED"` — unconditionally, then tries `sendEscalationAlert()` (`lib/owner-alerts.ts`); a missing owner chat, a missing bot token or an unreachable Bot API is logged and swallowed, so Telegram is a notification channel and never the source of truth (the dashboard bell and `/notifications` read `escalatedAt`). An empty tool `reason` falls back to the customer's own message, and the AI-outage path (`provider === "fallback"`) escalates the same way. Models do not always obey the "call the tool" rule, so after a reply is generated `handleIncomingMessage()` runs `promisesOwnerHandoff(reply)` (in `lib/escalation.ts`) whenever `toolEscalated` is false: if the reply promises a handoff ("I'm sending this to my boss/oga right now…", "let me check with my boss", "my boss will reply you shortly", "I'll escalate this"), the escalation is written anyway. The patterns are deliberately narrow — the mandated receipt sentence ("My boss/oga will verify it and confirm your delivery shortly"), the booking confirmation and the payment instruction ("send the receipt here so my boss/oga can confirm") must NOT match, or every payment proof would silence the assistant. `tests/escalation.test.ts` pins both halves.
- Telegram channel: `app/api/telegram/webhook/route.ts` - parses a Telegram update, ignores anything without text, a voice note or a photo (stickers, joins, edits — always 200), finds the `Business` by `telegramChatId` + `channel: "TELEGRAM"`, upserts a `Customer` via the `businessId_phone` unique (phone=`chat.id`, name=`first_name`), calls the engine, and POSTs the reply to the Telegram Bot API. Silent on cap_hit/paused/failure. Voice notes are transcribed inline (`lib/stt.ts`). **Photos** (payment receipts) arrive as an array of sizes — the last entry is the largest — and are never handed to the vision pipeline as a Telegram URL: the webhook downloads the file with `getFile` → `https://api.telegram.org/file/bot<token>/<file_path>`, re-uploads it with the service role (`uploadFileToSupabase()` in `lib/supabase/storage-admin.ts`, public `receipts` bucket, key `{businessId}/{chatId}/{stamp}.{ext}` by `lib/supabase/storage-path.ts`) and only then calls `processImageMessage()`, passing the resulting public URL to the engine as `imageUrl`. That upload needs `SUPABASE_SERVICE_ROLE_KEY`: without it the customer gets "I can't open pictures right now" and a `console.error`, never a crash. A caption rides along as `caption` and is appended to the stored text. A paused (escalated / human-takeover) conversation skips vision entirely but still stores the picture row (`messageType: "image"`), so the owner sees the receipt in the dashboard.
- System prompt constraints (critical): must call search_products for any product/price/stock/availability/spec question (including follow-ups; memory not catalogue). Answer only from tool results; only say "no product" if count==0; only say out of stock if tool shows stock==0. The `--- BOOKINGS (APPOINTMENTS) ---` block makes `create_booking` mandatory once the customer has given service + date + time (`YYYY-MM-DD` + 24-hour `HH:MM`, Lagos time), forbids inventing or backdating a slot, and forbids saying "booked" unless the tool returned `created: true`. Plain text only (no Markdown/formatting symbols). Never reveal exact stock quantities - only state available/in stock or out of stock/sold out. For multiple products, each on its own line as `Name Price` (no dash/colon/bullet), total on separate line.
- Tone: from Business.tone (validated by `isTone()` from `lib/business.ts`, fallback "friendly"). TONE_INSTRUCTIONS: formal, friendly (light emoji allowed in friendly tone instruction text, but reply must follow plain text rule), pidgin_friendly (Nigerian Pidgin). Tone appended last to bias model.

- In-chat payments: `app/api/payments/create-link/route.ts` — POST `{ amount (Naira), businessId, customerEmail }`. `businessId` must equal the session's business (`403` otherwise), `amount` is validated to ₦1–₦10,000,000 and converted to kobo, `customerEmail` goes through `isValidEmail()`, and `initializeTransaction()` from `lib/paystack.ts` returns `{ authorization_url, reference, amount }`. It is a one-off charge (no plan code), `callback_url` is `${NEXT_PUBLIC_APP_URL}/chat/success` (the public confirmation page at `app/chat/success/page.tsx`, session-free through the `/chat` prefix in `lib/public-routes.ts`), and the metadata is `{ type: "chat_payment", businessId }`. The link is stored on the message that carried it (`Message.paymentUrl`, https-only via `POST /api/conversations/[id]/messages` and echoed by the conversation GET). The billing webhook records nothing for it: an in-chat charge is neither a subscription nor a credit top-up, so `charge.success` with no plan and no local Transaction row is logged and ignored.
- Receipt-to-invoice: when a customer sends a payment receipt as an image through `POST /api/chat` — or as a Telegram photo, which the webhook stores in the public `receipts` bucket first and then hands to `processImageMessage()` itself — `lib/image-pipeline.ts` first describes it (`describeImage`) and, because a receipt is "not a product", reads it with `readReceipt()` in `lib/vision.ts` (Groq vision, strict JSON: amount / sender / date / reference, amount converted to integer kobo). The extracted details replace the stored description as `[Customer sent a payment receipt]: Amount … Sender … Date … Reference …`, and the engine hands the server-verified Storage URL to the `generate_invoice_from_receipt` tool (`generateInvoiceFromReceipt()` in `lib/tools.ts`). That function creates a **draft** `Invoice` only — one line item from the description, `vat: 0` (the receipt total already includes tax), `notes: RECEIPT_INVOICE_NOTE`, `receiptUrl` (a public object in Colly's own Supabase Storage bucket only — never a URL the model or the customer typed — and deduped so the same picture never produces two invoices) — and alerts the owner via `sendReceiptAlert()` in `lib/owner-alerts.ts`. All money on this path is integer kobo (`nairaToKobo`/`koboToNaira` in `lib/invoices.ts`); the AI can never write `paid`. `Invoice.status` now allows `paid`, reachable only through `PATCH /api/invoices/[id]` (`draft`/`sent` → `paid`, which also moves the customer to `dealStatus: "PAID"` on the CRM Kanban). The invoices list shows a `View Receipt` link and an `Approve Payment` button on drafts.

- Housekeeping: `app/api/health/route.ts` (liveness, no auth), `app/api/waitlist/route.ts` (WhatsApp waitlist: GET status for the signed-in business, POST with number normalisation + dedupe + in-process throttle), `app/api/business/nrs/route.ts` (NRS e-invoicing compliance fields on the business), `app/api/voice/transcribe-description/route.ts` (voice/image → product description).

## Booking System (Africa/Lagos)

- `Booking` (`prisma/schema.prisma`) is tenant-scoped (`businessId`) and customer-scoped (`customerId`), both `onDelete: Cascade`. `status` starts `PENDING` (`PENDING | CONFIRMED | CANCELLED`, narrowed by `isBookingStatus()`). `startTime`/`endTime` are `TIMESTAMPTZ(3)`: absolute instants, so the column never stores a wall clock and comparisons are correct whatever the session's `TimeZone` is.
- `lib/timezone.ts` is the only module that touches the zone. `LAGOS_TIMEZONE` is `"Africa/Lagos"`; `formatInLagosTimezone(date)` is `Intl.DateTimeFormat("en-NG", { timeZone, dateStyle: "full", timeStyle: "short" })` (e.g. "Tuesday, 3 November 2026 at 10:00"); `parseLagosDateTime(value)` honours an explicit offset (`Z`, `+01:00`), reads a zone-less wall clock as Lagos time, and returns `null` for impossible dates (`2026-02-31T10:00`) and for day-only strings (a booking needs a time).
- Two rules the module exists to enforce. Never format a stored instant with the runtime's own zone (`toLocaleString()` without `timeZone`): production runs in UTC, so a 10:00 WAT slot would render as 09:00. Never pass a zone-less string to `new Date()`: it means the *runtime's* local time, so the same request body would book a different moment on a UTC server than on a Lagos laptop.
- `lib/bookings.ts` mirrors `lib/invoices.ts`: `BOOKING_STATUSES`/`isBookingStatus()`, `DEFAULT_BOOKING_DURATION_MINUTES = 60`, `bookingEndTime(start, minutes = 60)` (pure instant arithmetic) and `serializeBooking()` (ISO-8601 UTC strings plus `startTimeLagos`/`endTimeLagos` and `timezone`, so no client re-implements the conversion). It also holds the slot parser the AI tool and any future scheduler share: `normalizeBookingDate()` (`2026-11-5` → `2026-11-05`), `normalizeBookingTime()` (`2pm`, `2:30 pm`, `14:00:00` → 24-hour `HH:MM`; `12am` → `00:00`) and `parseBookingSlot(date, time)` — normalise both halves, then `parseLagosDateTime()` as a Lagos wall clock, `null` for an impossible day such as `2026-02-31`.
- `create_booking` (declared in TOOLS, implemented by `createBooking()` in `lib/tools.ts`) is the AI's booking path: the model supplies `serviceName`/`date`/`time`, the tool always books for the **conversation's** customer, caps the service at 120 chars, parses the slot through `parseBookingSlot()`, refuses a past slot, sets `endTime` = start + 1 hour, leaves `status` to the schema default (`PENDING`) and does not insert the same customer + service + instant twice (`duplicate: true`). Its `BookingResult` mirrors `ReceiptInvoiceResult` — a business-rule failure is `{ created: false, error }` for the model, never a throw — and `message` is the exact line the AI repeats ("Booking created for Chidi on 2026-11-05 at 14:00").
- **Hotel stays.** `createBooking()` takes an optional `checkOutDate` (`YYYY-MM-DD`, the hotel mode's second date). When it is present the record is a stay rather than a one-hour slot: `endTime` becomes the check-out instant (same time-of-day, read as a Lagos wall clock), `bookingNights(start, end)` in `lib/bookings.ts` supplies the whole-night count, `notes` is written as `Check-out 2026-11-08, 3 nights`, and the result echoes `checkOutDate` / `nights` / `endTimeLagos` with the message "Booking created for Ada from 2026-11-05 to 2026-11-08 (3 nights)". A check-out that is not after check-in (including the same day) or an impossible day is `{ created: false, error }`. Without `checkOutDate` nothing changes: one hour, `notes` null.
- Dashboard schedule: `app/(dashboard)/bookings/page.tsx` is a Server Component (`await connection()`, `requireAuth()` — staff included, working the diary is not owner-only) that reads the tenant's rows with `orderBy: [{ startTime: "asc" }, { id: "asc" }]` and `take: 100` (and says so when it truncates), rendering every instant through `formatInLagosTimezone()` server-side. `components/dashboard/bookings-list.tsx` is the client list (status badge, Confirm/Cancel on PENDING) and calls `updateBookingStatus()` in `app/(dashboard)/bookings/actions.ts`: a Server Action that re-reads the tenant with `getCurrentBusinessId()`, allows `PENDING → CONFIRMED | CANCELLED` and `CONFIRMED → CANCELLED` (never back to PENDING), validates the value with `isBookingStatus()` because a Server Action is a network endpoint, calls `revalidatePath("/bookings")` and returns `{ ok } | { ok: false, error }` (the client then `router.refresh()`es). The sidebar's `MANAGE` section links it with the `Calendar` icon.
- `POST /api/bookings` 401s without a session, validates `serviceName` (≤ 120 chars) / `notes` (≤ 1000) / `startTime`, `404`s a `customerId` that is not this business's, sets `endTime` to start + 1 hour, leaves `status` to the schema default, and returns `201 { booking }`. No credits or payments are involved.
- Migration `20261104000000_add_bookings` is hand-written (like `add_team_members`) rather than generated with `prisma migrate diff --from-schema-datasource`, which also reports the raw-SQL `product_name_trgm_idx` / `Business` timestamp drift left by the `qa_indexes` migration.

## Industry verticals (Hotel Management)

The vertical a business sells in is a stored flag, not a separate product: `Business.industry`
(`RETAIL | HOTEL | SERVICES`, default `RETAIL`) plus one persona and one landing page per vertical.
`lib/business.ts` owns the vocabulary — `INDUSTRIES`, `Industry`, `isIndustry()`, `DEFAULT_INDUSTRY`,
`INDUSTRY_LABELS`, `industryFromSlug()` (URL form: `hotel`, `HOTEL`, ` Hotel `, and `service` as a
sibling of `services`; unknown/missing → `null`) and `industrySlug()`. `serializeBusiness()` reads an
unknown stored value as `RETAIL`, so a hand-edited row can never switch on a persona nobody reviewed.

- **Signup.** `/hotels` links to `/signup?role=business&industry=hotel`. `app/(auth)/signup/page.tsx`
  reads `searchParams.industry` after `await connection()`, normalises it with `industryFromSlug()`,
  and passes it to `SignupClient` → `BusinessSignupForm`, which renders it as a hidden `industry`
  field next to `plan`/`channel`. The `signup()` server action in `lib/auth-actions.ts` re-validates
  with `isIndustry()` (a hidden field is client-controlled) and writes `industry: industry ??
  DEFAULT_INDUSTRY` on a new Business row — and updates an adopted, pre-created tenant too, exactly
  like `selectedPlan`. So a hotel that signs up from the landing page lands in Hotel mode.
- **Settings.** `app/(dashboard)/settings/page.tsx` has an `INDUSTRY` section with a `<select>` over
  `INDUSTRIES` (labels from `INDUSTRY_LABELS`, guarded by `isIndustry()` on change), submitted with
  the rest of the form; `PATCH /api/business` validates it (`Industry must be one of: …`, 400) and
  stores it on the caller's own business. Like tone, it is a profile field, not an owner-only setting.
- **The persona.** `buildSystemPrompt()` in `lib/chat-engine.ts` appends `HOTEL_PERSONA` when
  `business.industry === "HOTEL"` — before the tone instruction, which stays last. The text is the
  contract: "HOTEL MODE: You are a hotel receptionist… you must ask for their Check-in Date and
  Check-out Date… Calculate the total cost based on the number of nights. Once they agree, use the
  `create_booking` tool. Do not book unless you have both dates." A `HOTEL BOOKING FIELDS` sentence
  tells the model where each half goes (`serviceName` = room, `date`/`time` = check-in,
  `checkOutDate` = check-out, 14:00 + say so when the guest names no time) and that a nightly rate
  must come from `search_products`. `handleIncomingMessage()` therefore selects `industry` with the
  rest of the business profile; nothing else about the engine changes.
- **The landing page.** `app/(marketing)/hotels/page.tsx` is a prerendered Server Component:
  `pageMetadata({ path: "/hotels" })` + `softwareApplicationJsonLd()` (no `FAQPage` — the homepage's
  `<FAQ />` owns that node), then `<Hero>` with hotel copy, a `HOTEL_BENEFITS` grid ("Instant rate
  quotes", "Automated deposits", "Check-in and check-out, one booking", "Multilingual guest support",

## Conventions / gotchas

- Keep chat replies plain text only (see SYSTEM_PROMPT_RULES line with extensive formatting ban). Never add Markdown.
- Never reveal exact stock quantities in responses - only availability states.
- Tool calling is mandatory for product questions; chat enforces with explicit rules and follow-up note.
- Human takeover: `conversation.pausedUntil` gates AI replies (returns paused true if active). Agent messages use sender "agent".
- Channels: `Business.channel` is one of `TELEGRAM`, `DISCORD`, `WEB_CHAT`, `WHATSAPP` (`lib/business.ts#isChannel`, schema enum `Channel`). Telegram, Discord and Web Chat are live and self-serve; WhatsApp is a **manual onboarding waitlist** (`WhatsAppWaitlist` model + `/api/waitlist` + the form on `/settings/ai-line`), so never promise a self-serve WhatsApp connection. Plans are one unified tier set for every channel — `green` (₦15,000 → 23,000 credits), `blue` (₦25,000 → 41,000), `black` (₦50,000 → 90,000), plus the permanent `free` tier (80 credits / 30 days). `lib/plans.ts` is the only source of prices, grants, reply costs and reset wording (`getPlanLimits`, `getPlanPrice`, `getMonthlyCredits`, `bonusDescription` / `bonusCreditsBadge` / `creditReplyCalculator`); the Paystack plan-code lookup is `getPaystackPlanCode()` in `app/api/billing/checkout/route.ts`, not in `lib/plans.ts`. Bonus copy is always quoted in **Telegram messages** — `bonusDescription` and `bonusCreditsBadge` both advertise "Free Telegram Messages", derived by `bonusStandardReplies()` (bonus ÷ 5): WhatsApp costs 80 credits and is waitlist-only, so no plan card may advertise WhatsApp messages or replies, and `tests/plans.test.ts` fails if one does. There is no per-channel tier split and no `channelForTier`/`plansFor` helper any more.
- Credits (split wallet, 1 credit = ₦1): `Business.planCredits` is the plan's monthly allowance — a successful plan charge OVERWRITES it with the tier's grant (`getMonthlyCredits`) in `app/api/billing/verify/route.ts` and both `charge.success` / `invoice.payment_success` in `app/api/billing/webhook/route.ts`, so unused allowance never rolls over. `Business.topUpCredits` is what the business paid for: top-up purchases INCREMENT it and nothing ever resets it. Replies cost 5 credits on Telegram/Discord/Web Chat and 80 on WhatsApp (`getAiReplyCreditCost`); `chargeAiReply` in `lib/chat-engine.ts` spends `planCredits` first then `topUpCredits` inside a `prisma.$transaction` compare-and-swap (retried up to 3 times), and every gate (`auth-guards`, chat engine, conversations API, UI) sums them with `totalAvailableCredits()`. Manual replies are free. `CREDITS_RESET_DISCLAIMER` (lib/plans.ts) is the exact customer-facing wording. Dashboard header shows plan + credit pills (`components/dashboard/plan-chip.tsx`, total with a plan/top-up tooltip); Plans page is Telegram-first. New signups land on the permanent Free plan (`plan: "free"`, `planStatus: "inactive"`, `planCredits: FREE_PLAN_LIMITS.credits` = 80, `topUpCredits: 0`); the 7-day trial is retired, so legacy rows stored as `trial` / `trialing` are read as Free everywhere. The Free 80 is re-granted lazily by `ensureFreeGrant()` in `lib/credits.ts`: once `Business.lastFreeGrantAt` is more than 30 days old it resets `planCredits` to `FREE_PLAN_LIMITS.credits` and stamps the field, using a compare-and-swap `updateMany` on `plan` + the stale stamp so a concurrent paid upgrade (or a parallel request) is never clobbered, and `topUpCredits` is never touched; it returns the same row with the fresh balance. Callers are `requireAiEnabled()` (lib/auth-guards.ts, before any gate so paused-AI accounts still refresh), `GET /api/billing/usage` (dashboard header pills + billing/credits pages) and the AI dashboard page (`app/(dashboard)/ai/page.tsx`), so the balance refreshes without waiting for an AI reply. There is also a scheduler: `/api/cron/maintenance` (Bearer `CRON_SECRET`) sweeps every business through `downgradeExpiredPlan` + `ensureFreeGrant`, so a dormant tenant still refreshes.
- Plan expiry: `downgradeExpiredPlan()` (lib/credits.ts) runs first inside `requireAiEnabled()`, before `ensureFreeGrant` and every gate. It demotes a paid row to Free — `plan: "free"`, `planStatus: "inactive"`, `planCredits: 80`, `lastFreeGrantAt: now`, `subscriptionStatus: "inactive"`, dunning fields cleared — when `planExpiresAt` is past AND `planStatus !== "active"` AND any dunning grace has lapsed; `active` rows are never touched (a late renewal webhook must not cut off a paying customer) and the write is a compare-and-swap on `plan` + `planStatus`, so a concurrent renewal wins. It runs first in `requireAiEnabled()` AND at the top of `GET /api/billing/usage`, so the dashboard plan chip and billing pages drop to Free on the next load instead of waiting for an AI reply.
- Auth linking: seeded/demo users have `supabaseUserId` null; signing up with matching email adopts the row. A signed-in session with no tenant throws (not redirect) to avoid login loop.
- Team Collaboration (owner + invited staff): `lib/team.ts` owns the vocabulary — `TEAM_ROLES` (`OWNER` | `STAFF`), `isTeamRole`, `OWNER_ONLY_PATHS` (`/settings/billing`, `/settings/ai-line`, `/settings/team`) with `isOwnerOnlyPath()` (exact or sub-path, never a look-alike prefix), and the bounce constants (`STAFF_DENIED_PARAM`/`VALUE`/`MESSAGE`/`REDIRECT` → `/dashboard?denied=staff_restricted`). `lib/auth.ts#loadTenant` resolves the owner's `User` row first (role `OWNER`) and falls back to a `TeamMember` matched **case-insensitively by email** (`STAFF`); the `User` row always wins, so an address that owns a business can never act as staff. `AuthUser.role` is what the guards read: `requireOwner()` (pages, redirects to the bounce) and `requireOwnerApi()` (`{ ok: false, response }` — 401 signed out, 403 `STAFF_DENIED_MESSAGE` for staff). The proxy skips `/api`, so **every owner-only mutation needs the route-level guard** (`requireOwnerApi()` in `billing/{checkout,credits/checkout,cancel}`, `telegram/connect`; inline `user.role !== "OWNER"` in `discord/actions.ts` and for `ownerTelegramChatId` in `PATCH /api/business`). `lib/supabase/proxy.ts#resolveTenantRole` bounces a STAFF session off an owner-only page; the dashboard page reads the `?denied=` flag and mounts `components/dashboard/staff-denied-toast.tsx` (the proxy never renders HTML). The shell hides the owner-only links from staff (`isOwner` from the layout's `user.role`). Staff are otherwise first-class: `getCurrentBusinessId()`/`getCurrentUser()` stay role-blind so the inbox, products, customers and invoices all work. Team management is `GET`/`POST`/`DELETE /api/team` (owner-only, keyset paginated): an invite only pre-authorises the address — the person signs up with it, and deleting the row cuts access on their next request. `TeamMember.email` is unique table-wide, so one address belongs to exactly one business. The owner-facing screen is `app/(dashboard)/settings/team/page.tsx` — a Server Component that calls `requireOwner()` and reads the first page of staff straight from Prisma (cursor handed to the client, so no silent truncation), rendering `components/dashboard/team-manager.tsx` for the invite form, the "Owner (you)" row and the remove confirmation (a `Modal`) — every mutation still goes through `/api/team`, so the page's guard only decides who may *see* it. The sidebar's "Team Members" link (`SECONDARY_ITEMS`, filtered with `isOwnerOnlyPath()` for staff) and the `TEAM MEMBERS` card on `/settings` are owner-only; `GET /api/business` returns `role` so the client-side settings page can hide the owner cards without a second call.
- Supabase server client cookie writes ignored in Server Components - by design, proxy handles rotation.
- Prisma logs: errors/warns in dev, errors only in prod.
- Logging: production-visible events (owner alert delivered, provider switch, billing webhook, payout) use `console.info` / `console.warn` / `console.error`. Anything that is only useful while debugging — a translated Pidgin query, a provider payload, an incoming Discord body, an escalation trace — goes through `debugLog()` from `lib/logger.ts`, which is a no-op in a production build. Never `console.log` a customer message, an email address or a payment payload: hosting log retention is the cheapest PII leak there is.
- Printing: the only page that prints a designed sheet is `/settings/qr-code`. `app/globals.css` hides `[data-print-hide]` on every route (sidebar, header, mobile tab bar, page toolbars, **the sitewide `Footer` and the floating Colly assistant**), but everything that unwinds the dashboard shell's full-height/scrolling boxes is scoped to `body[data-print-qr]` — a marker the QR page sets in a `useEffect` and deletes on unmount, with `[data-print-flush]` on the containers that must lose their padding. Keep that scoping: unscoped, printing an invoice or an inbox thread would drop its layout too. The card itself is `[data-print-card]` (90mm, 62mm canvas, `print-color-adjust: exact`, `break-inside: avoid` so it lands on one sheet).
- What the QR card carries is a contract, not a design choice: the Colly lockup small (`/logo.svg` + "Colly"), the business's own name big, the QR code, then `QR_CARD_TAGLINE` ("Scan to chat with our AI Assistant") and `QR_CARD_SUBLINE` ("Instant replies. Available 24/7.") from `lib/qr-card.ts`. No URL line, no navigation, no entity disclaimer — the footer carries `data-print-hide` precisely so those columns cannot print under the card. The PNG download is that same card drawn by `drawQrCard()` (`lib/qr-card.ts`: 1080px wide, transparent rounded corners, logo + name + QR + both lines, name auto-fitted to three lines) and saved as `colly-qr-<id>.png` by `qrCardFileName()`; it is not a bare QR square. The browser's own date / page-title / URL header is removed by an `@page { margin: 0 }` style tag the page injects while it is mounted (scoped there so invoice prints keep normal margins), with 12mm body padding in print so nothing hugs the paper edge.
- Error boundaries: `app/error.tsx` (whole app), `app/(dashboard)/error.tsx` (dashboard shell, so one broken page does not throw the workspace back to the marketing 404) and `app/global-error.tsx` (root layout failures). Next 16 passes **`retry()`**, not the pre-16.3 `reset()`. `global-error` replaces the root layout, so `globals.css` is not loaded there — its styles must be inline.
- Business tone defaults/fallbacks: unknown stored tone falls back to "friendly" in prompt building.
- SearchProducts returns max 5 matches; chat returns count/products to model.
- Analytics: the Umami `<Script>` is rendered exactly once, in the root `app/layout.tsx`, so marketing, auth and dashboard routes all report pageviews. Never add another copy in a nested layout/page (the marketing layout used to have one) — pageviews would be counted twice. Pageviews for App Router (client-side) navigation are sent by `components/analytics/umami-tracker.tsx`, which the layout mounts (inside a `Suspense` boundary, because it uses `useSearchParams`) only when `NEXT_PUBLIC_UMAMI_WEBSITE_ID` is set; the script therefore carries `data-auto-pageview="false"` — the script's own `history.pushState` hook plus the tracker would report every route twice, so the tracker must stay the only sender. Custom events go through `trackEvent(name, data)` in `lib/analytics.ts`, which is a safe no-op during SSR or when the script is missing. The `signup` event (`{ role: "business" | "agent" }`) is fired by `components/auth/business-signup-form.tsx` when `signup()` returns the email-verification state, and by the agent form in `app/(auth)/signup/signup-content.tsx`. A business signup that the server action redirects straight to `/dashboard` (email confirmation off) has no client-side success state, so it is pageview-only; covering it needs a marker (cookie or `?welcome=1`) read on the dashboard.
- Microsoft Clarity (optional session recordings) is the inline snippet in the root layout's `<head>`, rendered with `next/script` `strategy="beforeInteractive"` (`id="microsoft-clarity"`) only when `NEXT_PUBLIC_CLARITY_ID` is set. In the App Router that strategy queues the snippet in the server HTML as a `self.__next_s` entry and the app bootstrap runs it from `document.head` before hydration — `afterInteractive` would defer it to a client effect. It is listed as a processor in `app/(public)/privacy/page.tsx` — keep that list in step with `app/layout.tsx`.
- Next.js 16 experimental flags enabled: `agentFeedback: true`, `cacheComponents: true`, `partialPrefetching: true`. Turbopack configured for CSS. Do not remove the auto-generated Next.js agent rules block.
